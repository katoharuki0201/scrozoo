# データベース設計

## 1. 設計対象と前提

Better Auth が管理する `user`、`session`、`account`、`verification` は認証スキーマとして扱い、本書では変更しない。

業務スキーマは、要件定義、決定事項、API 定義、画面遷移、技術構成を基に設計する。主な前提は次のとおり。

- 投稿者アカウントと月額応援プランは動物園単位
- 動画とギャラリー投稿の対象動物は、所属動物園と一致する
- 月額料金は500円、投げ銭は100円から3,000円まで
- 決済は Stripe Sandbox のみだが、状態と履歴は保存する
- QR 認証で発行した投稿権限は対象動物園に限り2時間有効
- コメント、ギャラリー、課金履歴、お気に入り関係は退会後も保持する
- 動画と画像の実体は R2 に保存し、DB にはオブジェクト情報のみ保存する

## 2. エンティティ・属性定義

| エンティティ | 主キー | 主な属性 | 主な業務ルール |
| --- | --- | --- | --- |
| ユーザープロフィール | `userId` | 自己紹介、退会日時、作成・更新日時 | 認証ユーザーと1対1。退会は論理状態として保持 |
| メディア | `id` | アップロード者、R2キー、用途、MIME、サイズ、状態、完了・削除日時 | R2キーは一意。動画・画像の実体は保持しない |
| 動物園 | `id` | 投稿者ユーザー、slug、名称、説明、地域、住所、プロフィール画像、状態 | 1投稿者につき1動物園 |
| 動物園SNS | `id` | 動物園、プラットフォーム、URL | 同一動物園・同一プラットフォームは1件 |
| 動物 | `id` | 動物園、名称、種、説明、プロフィール画像、状態 | 必ず1動物園に所属 |
| 動画 | `id` | 動物園、対象動物、投稿者、フル動画、5秒版、説明、尺、公開状態、公開日時 | 対象動物は動画の動物園に所属。最大60秒 |
| タグ | `id` | 名称、slug | slugは一意 |
| 動画タグ | `videoId + tagId` | 作成日時 | 動画とタグの多対多中間 |
| 月額契約 | `id` | 利用者、動物園、料金、状態、Stripe識別子、契約期間、解約情報 | 動物園単位、500円。利用者・動物園ごとの有効契約は最大1件 |
| 月額契約イベント | `id` | 契約、Webhook、種別、金額、対象期間、Stripeオブジェクト、発生日時 | 加入・更新・解約予約・終了・失敗を履歴として保持 |
| コメント | `id` | 動画、投稿者、本文、投稿時サポーター状態、投稿日時 | ログインユーザーが投稿。本文は1〜1,000文字 |
| 投げ銭 | `id` | 利用者、動物園、動物、動画、確定コメント、入力本文、金額、決済状態、Stripe識別子 | 100〜3,000円。成功時のみコメントを確定 |
| お気に入り | `userId + videoId` | 登録日時 | 同じ動画を重複登録しない |
| 来園QR | `id` | 動物園、トークンハッシュ、状態、有効期限、失効日時 | 生の署名トークンは保存しない。MVP では無期限とし、有効期限・失効日時は使用しない |
| 来園投稿権限 | `id` | 利用者、動物園、QR、有効期限、発行日時 | QRと投稿先の動物園が一致。検証後2時間有効 |
| ギャラリー投稿 | `id` | 投稿者、動物園、任意の対象動物、来園投稿権限、画像、タイトル、公開日時 | 権限の利用者・動物園が投稿と一致。即時公開 |
| チャットメッセージ（将来用） | `id` | 動物園、投稿者、本文、保存期限、投稿日時 | MVP では使用しない予約済みスキーマ |
| Stripe Webhookイベント | `id` | 種別、対象オブジェクト、処理状態、エラー、受信・処理日時 | StripeイベントIDを主キーにして二重反映を防止 |

## 3. 論理設計

### リレーション

- 認証ユーザー 1 : 1 ユーザープロフィール
- 認証ユーザー 1 : 0..1 動物園（投稿者）
- 動物園 1 : N 動物、動画、SNS、契約、投げ銭、QR、投稿権限、ギャラリー
- 動物 1 : N 動画、投げ銭、ギャラリー
- 動画 N : M タグ
- 動画 1 : N コメント、投げ銭、お気に入り
- 月額契約 1 : N 月額契約イベント
- 来園QR 1 : N 来園投稿権限
- 来園投稿権限 1 : N ギャラリー投稿
- 動物園・動物・動画・ギャラリー投稿は必要なメディアを参照する。1つの動画はフル版とプレビュー版を別メディアとして持つ

### 整合性

- `video(animalId, zooId)` は同じ組の `animal(id, zooId)` を参照する。
- `tip(videoId, zooId, animalId)` は同じ組の動画を参照する。
- `visitPermit(qrCodeId, zooId)` は同じ組の来園QRを参照する。
- `galleryPost(visitPermitId, userId, zooId)` は同じ組の来園投稿権限を参照する。
- ギャラリーに対象動物を設定する場合、その動物は投稿先動物園に所属する。
- サポーター一覧は有効な月額契約と成功済み投げ銭から導出する。
- サポートログは月額契約イベントと投げ銭から導出する。
- フル動画閲覧権限は、月額契約の状態・契約期間から都度判定する。

### 正規化方針

- 動物園、動物、動画、タグ、メディアを分離し、表示情報の重複を避ける。
- 契約の現在状態と履歴を分離し、状態更新後も過去イベントを失わない。
- 投げ銭には決済確定前の本文を保持し、成功後に通常コメントへ関連付ける。
- 集計値、80%・20%の分配額、サポーター一覧は保存せず、元データから計算する。

## 4. 物理設計

### Turso / SQLite 方針

- テーブル名・カラム名は `snake_case`、Drizzle のプロパティ名は `camelCase`
- IDはAPI仕様に合わせてUUIDまたはULIDの `TEXT`
- 日時はUTCのUnix時刻ミリ秒を `INTEGER` で保存
- 真偽値はSQLiteの `INTEGER` にDrizzleのboolean modeを使用
- 金額は誤差を避けるため円単位の `INTEGER`、通貨は `jpy`
- enum相当値は `TEXT` と `CHECK` 制約で限定
- 外部キーは履歴保持対象を原則 `RESTRICT`、純粋な中間表のみ `CASCADE`
- 退会は認証ユーザーを物理削除せず、`withdrawn_at` で管理

### インデックス方針

- 一覧のカーソルページング用に、動物園・利用者・状態と日時の複合インデックスを置く。
- 動画検索用に動物園、対象動物、公開状態、公開日時、タグのインデックスを置く。
- 契約は利用者・動物園・状態、投げ銭は利用者・動物園・動画・日時で検索できるようにする。
- ギャラリーは動物園と公開日時、本人ギャラリーは利用者と公開日時で検索できるようにする。
- Stripeの各識別子、冪等キー、R2オブジェクトキーは一意にする。

## 5. 実装対象外

要件で対象外となっている実精算、返金、本人確認、モデレーション、通報、フォロー、通知、分析専用データは設計しない。既存の `chat_message` テーブルはマイグレーション互換性のため残すが、MVP の API・画面からは使用しない。
